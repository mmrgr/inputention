# Predict Next Inputs 中文说明

`predict-next-inputs` 是一个 Codex skill，用于预测用户下一步可能输入的内容、澄清用户的模糊输入，并把用户通过序号选择的候选项补全成完整可执行的真实意图。

它的核心目标是：减少用户输入成本，避免助手在用户表达不完整时答偏，同时让对话可以通过“序号 + 少量补充内容”的方式继续推进。

## 功能概览

这个 skill 有三项核心能力：

1. **预测下一步输入**

   当用户要求“预测我接下来可能问什么”或“给我 9 个可能的后续输入”时，skill 会基于当前对话上下文，生成 9 个最可能的下一步输入。

2. **澄清模糊输入**

   当用户只输入关键词、半句话、模糊动作、指代不明内容，或缺少关键对象时，skill 不会直接猜测并回答，而是生成 2-9 个最可能的完整意图候选，让用户选择。

3. **序号补全执行**

   当用户回复序号，并可选地补充细节时，skill 会把补充内容填入对应候选项的占位符，拼合成完整用户意图，然后继续完成任务。

## 典型使用场景

适合使用这个 skill 的场景包括：

- 用户想让助手预测下一步可能输入什么。
- 用户希望用序号选择来减少输入成本。
- 用户只输入了一个关键词，例如 `VPN`、`报错了`、`简历`、`论文`、`邮件`。
- 用户输入了英文模糊表达，例如 `won't open`、`not working`、`translate this`。
- 用户说“帮我看看”“改一下”“这个不对”，但没有说明对象或具体问题。
- 用户在候选列表后回复 `2；A；B`、`我选2`、`I choose 2`、`use #2` 等。

## 三种工作模式

### 1. 下一步输入预测模式

当用户明确要求预测后续输入时，进入这个模式。

例如：

```text
请你预测我接下来最可能问的 9 个问题。
```

或：

```text
Predict my most likely next inputs.
```

此时 skill 会：

- 分析当前对话上下文。
- 判断用户正处于理解、设计、修改、纠错、执行、比较、延展或验证等哪种阶段。
- 内部生成不少于 12 个候选。
- 筛选出最合理的 9 个。
- 按用户最可能输入的概率从高到低排序。
- 输出完整、自然、可直接使用的 9 个输入。

这个模式固定输出 9 项，除非用户明确要求其他数量。

### 2. 模糊输入澄清模式

当用户输入不够明确，直接回答很可能答偏时，进入这个模式。

典型触发情况：

- 只有关键词：`VPN`、`报错`、`简历`、`论文`、`邮件`、`翻译`。
- 只有模糊动作：`帮我看看`、`改一下`、`写一下`、`怎么搞`。
- 缺少处理对象：`翻译一下` 但没有提供文本。
- 指代不明：`这个不对`、`它坏了`、`还是不行`。
- 多义表达：`打不开` 可能指网页、软件、文件、设备、账号或项目。
- 缺少关键条件：不同补充信息会导致完全不同的回答路径。
- 高风险或高成本场景：代码报错、故障排查、法律、医疗、金融、安全等领域信息不足。

此时 skill 会输出 2-9 个候选，不强行凑满 9 个。只有当确实存在很多合理解释时，才列满 9 项。

### 3. 序号补全执行模式

当用户在预测或澄清列表之后回复序号时，进入这个模式。

支持的输入形式包括：

```text
2
2；A；B
2; A; B
2: A
2. A
第2个
我选2
选 2
用第二个
按第 2 条来
option 2
I choose 2
use #2
go with the second one
```

执行流程：

1. 找到最近一次预测或澄清列表。
2. 读取用户选择的编号。
3. 提取该候选项中的占位符。
4. 按从左到右的顺序填入用户补充的内容。
5. 如果用户补充内容多于占位符，将多余内容作为附加要求。
6. 如果用户补充内容少于占位符，且无法可靠推断，提示用户缺少哪些信息。
7. 拼合成完整意图后，继续回答用户真正想问的问题。

## 多语言支持

这个 skill 支持中文、英文以及其他语言场景。

基本原则：

- 用户主要使用中文，就用中文输出候选、提示和回答。
- 用户主要使用英文，就用英文输出候选、提示和回答。
- 用户中英混合时，以用户主要语言为准。

中文、日文或混合 CJK 场景中，占位符使用中文方括号：

```text
【报错内容】
【需要翻译的文本】
【目标风格】
【电脑系统】
```

英文和多数其他语言场景中，占位符使用英文方括号：

```text
[error message]
[text to translate]
[target style]
[operating system]
```

补全执行时，两种占位符格式都可以识别。

## 触发规则

### 应触发预测模式

当用户明确要求生成可能的下一步输入时触发。

例如：

```text
预测我下一步可能会问什么。
```

```text
给我 9 个我接下来可能输入的问题。
```

```text
What might I ask next?
```

### 应触发澄清模式

当用户输入存在较高不确定性时触发。

较高不确定性通常意味着：

- 缺少任务对象。
- 缺少关键条件。
- 指代对象不清楚。
- 存在多个差异很大的解释。
- 直接回答很可能偏离用户真实意图。
- 回答路径依赖于尚未提供的重要信息。

例如：

```text
打不开
```

```text
报错了
```

```text
won't open
```

```text
translate this
```

### 不应触发澄清模式

如果用户意图已经足够清楚，应直接回答。

例如：

```text
帮我写一封向老师请病假的邮件。
```

此时应直接写邮件。

例如：

```text
把这句话翻译成英文：我今天身体不舒服，想请一天假。
```

此时应直接翻译。

如果只是缺少一些不影响主要回答的小细节，可以先做合理假设并说明，然后继续完成任务。

## 占位符规则

占位符必须清楚说明用户需要补充什么。

推荐中文占位符：

```text
【报错内容】
【软件名称】
【电脑系统】
【需要翻译的文本】
【需要润色的文本】
【目标风格】
【具体现象】
【已尝试的方法】
【最终产物类型】
```

推荐英文占位符：

```text
[error message]
[software name]
[operating system]
[text to translate]
[text to polish]
[target style]
[specific symptom]
[steps already tried]
[final artifact type]
```

避免使用模糊占位符：

```text
【内容】
【东西】
【情况】
[content]
[thing]
[stuff]
```

通常每个候选项使用 1-4 个占位符最合适。占位符过多会增加用户选择和补全成本。

## 补全示例

### 中文示例

助手给出的候选项：

```text
1. 我在运行【软件/代码/命令】时出现报错：【报错内容】，请帮我分析原因。
```

用户回复：

```text
1；Python 脚本；ModuleNotFoundError: No module named pandas
```

拼合后的真实意图：

```text
我在运行 Python 脚本时出现报错：ModuleNotFoundError: No module named pandas，请帮我分析原因。
```

之后助手应继续解释 `pandas` 模块缺失的原因，并给出安装与排查方法。

### 英文示例

助手给出的候选项：

```text
1. I cannot open [website/app/file/device], please help me troubleshoot the cause.
```

用户回复：

```text
1; a PDF file; it says the file is damaged
```

拼合后的真实意图：

```text
I cannot open a PDF file, please help me troubleshoot the cause. Additional requirement: it says the file is damaged.
```

之后助手应继续给出 PDF 文件损坏的排查和修复建议。

## 候选项质量标准

每个候选项都应该：

- 是一句完整自然语言请求。
- 像真实用户会输入的话。
- 尽量保留用户原始关键词。
- 用户选择后可以直接执行。
- 不加入用户没有提供的事实。
- 不推断用户隐私或敏感背景。
- 与其他候选项有实质区别。
- 按可能性从高到低排序。
- 使用清晰、可填写的占位符。

候选项不应该：

- 写成“翻译请求”“调试问题”这类标签。
- 多个选项只是换一种说法重复同一件事。
- 为了凑满 9 项而加入低相关选项。
- 把推测写成事实。
- 擅自补充用户没有表达的立场、身份、情绪或结论。

## 安全与准确性边界

skill 必须避免过度解读。

例如用户说：

```text
老板没回我
```

不应补全为：

```text
老板故意冷落我，我该怎么办？
```

更合适的候选是：

```text
我的老板还没有回复【某条消息/某个请求】，请帮我判断下一步应该如何跟进。
```

在医疗、法律、金融、安全、心理危机等高风险场景中，如果信息不足，应优先澄清或提示需要专业帮助，不要基于模糊输入给出确定性结论。

如果拼合后的请求涉及新闻、价格、政策、法律、软件版本、医疗、金融等可能变化或高风险信息，助手应遵循当前系统的高准确性要求，必要时进行来源核验或联网查询。

## 设计原则

这个 skill 不应替用户武断决定真实意图，而是帮助用户更省力地表达意图。

当用户意图清楚时，直接回答。

当用户意图不清楚但可以归纳出合理候选时，主动给出高质量序号选项。

当用户选择候选后，正确补全意图并继续完成任务。
